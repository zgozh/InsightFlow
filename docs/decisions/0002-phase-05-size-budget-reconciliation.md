# 决策：Phase 5 先执行已证明安全的删除，再复核仓库预算

背景：Phase 0 把最终 tracked files 目标定为 850–1050、硬上限 1200。Phase 5A 对固定基线做静态审计，
已证明五批可安全删除 783 个文件，但预测仍有 2290 个文件。该预测把十个候选域之外的多项能力保守
列为 KEEP，不能证明 2290 是最终不可再缩的下限。

决策：先按 Phase 5A 清单依序执行 B1–B5，删除已经具备入口、动态引用、替代主链和测试证据的部分。
B5 完成后基于真实剩余 tree 做 Phase 5C 二次价值审计和预算复核。850–1050 暂不改写，也不作为删除
安全测试或破坏 KEEP 主链的理由；2290 同样不被接受为最终交付体量。

备选：一是现在强制达到 1200，代价是未经证据删除安全测试和核心 runtime，否决；二是直接把目标改成
2290 并结束瘦身，但 Phase 5A 仍存在保守 KEEP，证据不足，否决；三是在任何删除前继续扩大静态审计，
会重复分析一个即将大幅变化的 tree，成本高且结论很快过期，否决。

后果：Phase 5 至少包含一次已批准删除执行和一次删除后复核。最终预算可能基于真实 KEEP 成本调整，
但必须说明变更理由、不可删成本和简历/学习价值；每个删除批次独立提交。由于 B1→B5 存在依赖，整链
回滚必须按 B5→B1 逆序进行；“任意旧批次可在保留后续批次时单独 revert”不是有效承诺。
