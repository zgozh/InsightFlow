# Phase 6F3F16：直连接口核实真实 Agent→HTML 产物

## 目标与已知事实

固定本机验收栈为 `insightflow-acceptance-local`，入口 `http://127.0.0.1:29384`。6F3F14 的浏览器夹具在点击提交后立即同步检查 `/runs/stream` 计数并关闭页面；它没有等待异步请求，因此“0 次 stream”**不能证明**产品提交失败。6F3F15 已完成首页中文化，不属于本切片。现在用一次新的、独立的、真实认证请求，在 API/SDK 层判断 `deepseek-flash` → Agent 工具 → 沙箱 HTML artifact 是否能闭环；若产物存在，再用浏览器只读验证预览。

## 边界与实施

1. 先只读核对 HEAD、干净工作树、五个现有容器及健康状态。保持 `29384` 入口、五容器和三个命名卷；不运行全栈 Compose `up/down`，不重建、不清理数据。仅在已证实的最小代码修复需要部署时，按受影响服务最小范围更新。
2. 在现有代码中找出前端正常创建 thread/run 使用的认证接口和实际请求格式。优先复用已存在的认证试用 helper/测试账户；不要打印、保存或提交密码、API key、cookie、原始模型输出、用户私人内容。不要从 6F3F14 的不确定提交状态推断“没有 run”，也不要重放那条消息。
3. 创建**一个新的试用 thread**，用具体安全主题“星空”发**最多一次**真实用户请求，明确指定模型 ID 为 `deepseek-flash`。请求要求生成一个自包含、可点击交互、无需外部资源的简短 HTML 小惊喜并作为 artifact 交付。可用一个临时、gitignored 的本地脚本直接调用 Nginx/Gateway 认证 API 或仓库 SDK；不靠模拟点击浏览器来发模型请求。发出请求时异步等待实际响应/SSE 事件直至完成或有界超时，记录 HTTP 状态、`Content-Location`、thread/run ID 和事件类别；不要在发出请求后立即以空计数作结论。
4. 同一 thread/run 只读查询消息/工具轨迹，记录**工具名、稳定状态码、虚拟 artifact 路径**及关联关系。若有 HTML artifact，使用现有受权预览入口以同一账户打开，核实可见内容与一次点击交互；浏览器在这里仅作无模型请求的 UI 验证。不得将 API 成功等同于聊天 UI 提交成功，也不得把模拟预览当成真实产物。
5. 若一条链断开，按“请求/认证 → Gateway run → 模型 → 工具 → 沙箱文件 → artifact 绑定 → 预览”定位最早可证实的断点。若能确认一个**局部产品缺陷**，允许在本切片做最小修复、针对性测试、受影响服务的最小部署与**一次**新的验证；不得无证据扩大为架构改造或循环付费重试。若缺少凭据、外部模型故障、无法安全区分状态，停止并报告，不猜测、不重试。

## 验证与交付

本切片按 V3 的**单条真实产品链**验证，不运行全仓 pytest、前端 Rstest、全量 Playwright、全量 build 或数据库测试。无代码修复时，直接接口证据 + 必要的只读预览即足够；有代码修复时只跑直接受影响的测试/静态检查，已有证据未失效则不重跑。用非交互 HTTP 客户端，PowerShell `Invoke-WebRequest` 必须带 `-UseBasicParsing`；避免安全警告阻塞。

将真实结果、计数、成功/失败边界、是否触发第二次模型调用、是否产生可保留的试用 thread/artifact、任何实际修复和未验证项写入 `docs/acceptance/phase-06f3f16-direct-agent-artifact-trial.md`，同步 `docs/PROGRESS.md`。只提交本切片相关文件；`.reviews/` 临时脚本与截图不提交，保持工作树干净，不 push。报告必须明确区分 API 闭环、聊天 UI 提交链、artifact 预览这三项各自的证据；绝不将未发生的步骤写成通过。完成后停在主会话复验，不自行进入下一阶段。
