# 经营分析工作流

这个 skill 规定**顺序**与**证据要求**，不实现任何 SQL 策略、访问控制或凭证访问。
权限判定、成本门禁、行数/字节上限与审计全部由平台的受控查询工具执行；你只需要按顺序使用它们，
并如实报告结果。

## 工具

- `inspect_business_catalog`
  列出当前用户可访问的数据源与已登记指标。没有参数——调用者身份由会话决定。
  先用它拿到合法的 `datasource_id`，不要凭空猜测数据源名称。
- `query_business_data`
  参数只有 `datasource_id` 与 `sql`。它在一次调用内完成计划与执行，返回稳定 `code`、有界结果
  与 `evidence`。
- `publish_analysis_report`
  参数只有 `title`、`artifact_path` 与 `evidence_ids`。它只登记报告索引，**不读文件内容**，
  也不接受 principal/thread/run/status/时间。它把这份报告挂到**当前登录用户**当前的这次分析会话上。
- 委派用现有的 `task` 工具；报告文件用现有 sandbox 工具写入 `/mnt/user-data/outputs`，
  再用 `present_files` 交付。

## 步骤

1. **确认问题**：先写清楚要回答的业务问题、时间范围与指标口径（分子分母、去重规则、时区）。
   信息不足时用现有的澄清能力向用户提问，不要用假设填补。
2. **查目录**：调用 `inspect_business_catalog`，从中选择**精确**的 datasource 与 metric。
   目录里没有的数据源或指标就是不存在的，不要构造替代名称。
3. **一次一条查询**：每次只调用一次 `query_business_data`，串行执行。不同时发起多条数据库查询，
   也不要为了"顺便多拿一点"而合并无关的查询。
4. **读结果**：返回 `code` 不是成功码时，如实把该稳定码报告给用户并说明下一步；不要重试同一条
   查询，也不要改用其他数据源绕过拒绝。`truncated` 为真时说明结果被上限截断，需要缩小范围。
5. **保留 evidence**：把返回的 `evidence` 原样交给后续步骤。`evidence_id` 是这条结果的确定性引用，
   `result_digest` 用于核对转述内容是否对应当前结果。
6. **委派 Data Analyst**：结果与 evidence 就绪后，用 `task` 委派一个 general-purpose subagent，
   在 prompt 里明确它的角色是 Data Analyst，任务只是统计、对比与制图建议。要求它只使用你给出的
   数字；缺失的数据必须标注为缺失，不得虚构或外推。
7. **委派 Reviewer**：分析就绪后再委派第二个 general-purpose subagent 作为 Reviewer。
   它的职责是核对数字与口径、检查每个结论是否引用了 `evidence_id`、以及风险与限制是否被披露。
   明确要求它**不要**查询数据库、不要创建子 Agent。
8. **最多一次定向修订**：Reviewer 指出问题时，按它的意见做一次针对性修订并重新复核。
   仍然不通过就如实返回失败与原因，不要伪造通过，也不要无限循环。
9. **交付**：通过后把报告写入 `/mnt/user-data/outputs`（Markdown，必要时附 CSV 或图），
   用 `present_files` 交付。
10. **登记报告索引**：**只有** `present_files` 成功之后才调用 `publish_analysis_report`，
   传入 `title`、`artifact_path`（必须与刚交付的 outputs 路径逐字一致）与该报告实际引用的
   `evidence_ids`。这一步只是登记索引，不会复制或上传文件。
    - 返回 `published` 表示索引已登记；
    - 返回 `existing` 表示这次是重试，索引里已经有同一份报告——这是正常结果，不要重复登记；
    - 返回 `report_conflict` 表示同一路径上已经登记过**内容不同**的报告。不要尝试覆盖，
      改用新的文件名，或如实说明这次没有登记成功；
    - 任何非成功 code 都必须如实报告，**绝不能把未登记的报告说成"已保存"**。
11. **最终回复**包含摘要、限制与风险、引用的 `evidence_id` 列表、artifact 链接，以及报告是否
    成功登记。不要展示思维链或工具调用的中间草稿。

## 回答纪律

- 每个数字都要能追溯到某条 `evidence_id`；没有 evidence 支持的推断必须写成推断并说明依据。
- 口径发生变化（时间范围、过滤条件、去重规则）时必须说明，不能把两种口径的结果混在一张表里。
- 平台拒绝一条查询时，那是策略结论而不是技术故障：如实转述稳定码，不要尝试绕过。
- 结果被截断、或某个维度缺失时，把它写进"限制"，不要用插值补齐。

## 不要做的事

- 不要在报告里粘贴原始 SQL、连接信息、账号、token 或任何凭据。
- 不要自己实现权限判断、行数限制或成本估算——这些由工具负责。
- 不要虚构数据源、表名、字段名或指标；只使用 `inspect_business_catalog` 返回的内容。
- 不要并行发起多条业务查询，也不要因为一次失败就自动重新查询。
- 不要在 `present_files` 之前登记报告，也不要在登记失败时声称报告已保存。
- 不要把 `publish_analysis_report` 当成"上传报告"——它只写索引，不复制文件。
- 不要提交 `artifact_path` 之外的路径（例如 `uploads/` 或带 `..` 的路径），也不要提交非
  `evidence_id` 的字符串。
